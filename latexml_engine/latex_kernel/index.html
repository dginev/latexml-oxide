Loading the LaTeX format on demand — the eager trigger list’s safety net.

TeX.pool installs the Perl-faithful autoload triggers (TeX.pool.ltxml L33-56: \documentclass, \newcommand, \begin, …), each a macro that expands to \@load@latex@pool <trigger>. Those fire eagerly, on a legitimate use, before any error is raised — and they stay exactly as Perl writes them.

But a curated list is incomplete by construction: real LaTeX has no “before the kernel” (latex.ltx is the format), so a document may legitimately open with any kernel command. Anything not on the list was simply undefined — stubbed as <ltx:ERROR/>, with the document derailing from there. The canonical witness is the “use this class if installed” idiom

\IfFileExists{proc-l.cls}{\documentclass{proc-l}}{\documentclass{amsproc}}

(arXiv 2605.25877 line 4, 2606.06905, 2606.09693, 2606.16723): with \IfFileExists undefined the conditional collapses, no class is ever selected, and the run cascades into Fatal:TooManyErrors. Same-host Perl LaTeXML fails identically — see docs/parity/KNOWN_PERL_ERRORS.md.

autoload_latex_kernel closes the gap generally: registered into latexml_core::binding::kernel_autoload, it is consulted at the two undefined-CS paths (gullet read_x_token, stomach invoke_token_undefined) instead of erroring, and answers “is this a LaTeX kernel command?” — if so the format loads and the token is retried. It subsumes the two Rust-only, witness-driven trigger accretions that used to sit in tex.rs’s list: \UseRawInputEncoding (witness 2403.19280) and \DocumentMetadata (witness 2305.08034), which are now just two instances of “a kernel CS used before the format loaded”.

§The membership oracle is the DUMP, not latex.ltx

The question that has to be answered before committing to a load is “what will be defined after LaTeX.pool loads?” — because “load it and see if that helped” would drag the kernel into genuinely plain-TeX documents on their first undefined CS.

The right oracle for that is latex.YYYY.dump.txt, and deliberately not the host’s latex.ltx. The dump is not a “YYYY artifact”: it is generated by our current code inside a pinned TL-YYYY container, and it is the executed result of that bootstrap — the state delta this engine actually reaches. latex.ltx is source text, so answering the same question from it would mean re-deciding every \def / \let / \csname / \@namedef / \ifx in the file, i.e. re-running the load we are trying to avoid. It is also the very artifact LaTeX.pool goes on to replay, so a catalogue built from it cannot disagree with what the load installs. Do not “correct” this to latex.ltx.

Only the backward direction exists. A control sequence newer than the ambient dump year is out of scope by design — we cannot predict a TeX Live that has not shipped, and the host TeX Live of that age does not have the command either, so reporting it undefined is correct. There is no forward-compat seam and none is wanted.

§Degraded (no-dump) branch

LoadFormat('latex') has two mutually exclusive branches (CLAUDE.md durable parity rule 1). On the degraded one — $LATEXML_NODUMP, or no dump reachable at all — there is no key set to test against, so latex_kernel_defines is always false and this mechanism never fires. Behaviour there is bit-identical to before: the Perl TeX.pool L33-56 trigger list remains the only mechanism.
